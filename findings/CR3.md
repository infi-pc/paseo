## Scope and verdict

**Candidate:** `554a140ee10fbcf6ecd501a7804a5c5e01d900c6` — Add workspace snoozing on GitHub and Linear status changes.
**Base:** its parent, `886a8690317a72c1177484c3f7358bf72d943cc3`.

**Verdict: not ready.** Three reproduced provider-handling defects violate scheduled checking or known-change-only wake behavior. A fourth finding records the missing populated browser verification required by the project.

Three independent reviewers covered correctness/reliability; API contracts/security/persistence/performance; and frontend/testing/maintainability/project standards. The orchestrator inspected the surviving findings, their callers, and counterexamples. Root instructions, `packages/server/CLAUDE.md`, and the relevant lifecycle, protocol, forms, and testing docs supplied the contracts.

The intended behavior is a third snooze mode that snapshots selected GitHub PR lifecycle/review decisions and linked Linear issue state IDs before hiding a workspace. It keeps exact identities, checks every five minutes or hourly, survives restarts, and wakes on any observed difference. Failed reads remain inconclusive; independently successful changes can still wake. Existing auto-archive eligibility takes precedence. CI and metadata changes are excluded.

- **CR3-4 — Impact:** One workspace returns to the sidebar and can notify spuriously, losing its snooze until the user recreates it. Field-level partial failures are assumed rare; their production prevalence was not measured. **Invariant:** failed observations must not become evidence for a baseline or wake. **Checked:** a legitimate successful `reviewDecision:null` must remain valid; wholly missing PRs already fail; successful aliases elsewhere should remain usable. The shared reader's partial-data extraction pre-dates this commit, but the new fixed-watch path turns an errored nullable field into a lifecycle decision. **Proof:** the runtime reviewer ran `node --import tsx /tmp/paseo-partial-review-repro.ts` against the production GitHub service and checker. Its runner threw `GitHubCommandError` with exit 1 and stdout containing otherwise valid PR data, `reviewDecision:null`, and `errors:[{message:"Something went wrong while executing your query",path:["t0","pullRequest","reviewDecision"]}]`. From an Approved baseline, the checker returned `{"status":"unblocked","reason":"PR #42 · Review: Approved → No decision"}` after one runner call. This is a controlled provider-response reproduction, not an observed GitHub outage. **Fix:** preserve GraphQL error paths through the adapter and exclude failed watched fields from successful observations while retaining healthy fields/targets. **Gate:** despite low estimated frequency, the reproduced behavior violates the explicit failed-read guarantee. Priority does not waive that guarantee.

## Open product question

Editing a status snooze currently offers only the targets saved in its baseline (`packages/server/src/server/workspace-snooze/status.ts:32`). A reviewer reproduced discovery returning `[state, review]`, then only `[review]` after saving a review-only watch, even while the same PR remained connected. Refresh cannot restore the omitted lifecycle switch. The workaround is unsnooze and recreate.

Whether editing must add targets was not explicit in the supplied plan, so this is a contract question rather than a gated defect. If supported, merge eligible choices with the preserved fixed identities; at minimum offer both lifecycle and review for an already watched PR without silently following a new branch.
